# План реализации

## 1. Контракт модели и базовый эксперимент

Согласовать таблицу исходных данных из project-brief.md. Отделить подтверждённые значения, диапазоны и допущения. Для каждого сценария зафиксировать конфигурацию, seed, начальное состояние, прогрев и измеряемый период.

## 2. Вертикальный срез ASRS-B

Одна аллея, один STU, ограниченный буфер, один доставщик, одна станция и несколько адресов. Реализовать полный цикл выдачи и возврата/приёмки по согласованным правилам. Сначала проверить один ящик и расчёт времени движения, затем серию заданий и блокировки при заполненном буфере.

Движение рассчитывать с ускорением и торможением. Для совместных осей STU время перемещения может определяться максимумом времён осей, для последовательных — суммой; выбор подтверждается устройством оборудования. Время передачи учитывать отдельно. Реальные API и события VC подбираются после проверки целевой версии.

## 3. Семейства компонентов

| Семейство | Ответственность |
| --- | --- |
| box / pallet / parcel | ID груза, габариты, масса, назначение |
| rack | Адреса и занятость, резервирование ячеек |
| stu | Очередь заданий, оси, каретка, передача, состояния |
| buffer | Ограниченная ёмкость и согласованная передача владения грузом |
| delivery-robot | Поездка, загрузка, выгрузка, зарядка, состояния |
| station | Очередь, обработка оператором, завершённые операции |
| dispatcher | Назначение задач и ресурсов, приоритеты |
| metrics | События, очереди, загрузка, задержки, производительность |

Предлагаемый контракт задания: task_id, load_id, source, destination, created_at_s, priority. Состояния: queued → assigned → executing → completed либо failed/cancelled. Груз в каждый момент имеет одного владельца; резервирование не считается физической передачей. Контракт пока проектный, требуется реализация и проверка в VC.

## 4. Масштабирование и эксперименты

Параметризовать число аллей, STU, доставщиков, станций и поток. Сравнивать конфигурации на одинаковых входных данных и наборах seed. Считать завершённые операции/h отдельно для inbound/outbound и каждой станции, среднее и p95 времени задания, длину очередей, доли busy/idle/blocked/charging.

Искать минимальный флот, выполняющий заданные требования во всех согласованных режимах. Дополнительно проверять отсутствие устойчивого роста очередей: высокая краткосрочная выдача ещё не доказывает устойчивую производительность.

## 5. Проверка и калибровка

Проверки: одиночная операция; предельные ёмкости; конкуренция за один ресурс; пустой склад; насыщенная нагрузка; зарядка; повторный reset/run; длительный прогон без потерь и дублирования грузов. Для большого склада оценить нагрузку от визуализации всех ящиков: допускается логический учёт занятости при согласованной визуализации активных грузов.

Калибровать времена и политики на одном наборе натурных измерений, проверять на другом. Для положительного фактического KPI использовать |model-real| / real × 100%; для нулевого значения согласовать абсолютный допуск. Проверять 5% по согласованному перечню KPI и условиям, а не только по суммарной выдаче. Указывать вариативность и число повторений.

## 6. Расширения

Два STU на аллею требуют зон безопасности, координации, предотвращения тупиков и проверки возможности разъезда. Это самостоятельный этап. Затем ASRS-P 3DS (сначала внутренний контур, затем транспорт) и сортировка. Совместимость компонентов RPro подтверждать пробным переносом, без обещания автоматической конвертации.

## Критерий готовности первой модели

Загружается в согласованной версии VC, выполняет полный цикл, допускает изменение числа доставщиков, выдаёт воспроизводимый отчёт KPI, проходит проверки сохранения грузов и ёмкостей. Результаты сверены с натурными измерениями либо явно помечены как некалиброванные.
