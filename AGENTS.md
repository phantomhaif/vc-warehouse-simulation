# Инструкции для ИИ-агентов команды

## Начало работы

1. Прочитайте README.md, docs/project-brief.md, docs/implementation-plan.md и CONTRIBUTING.md.
2. Проверьте `git status`, текущую ветку и задачу. Не перезаписывайте чужие незакоммиченные изменения.
3. Найдите нужный компонент по `components/*/manifest.json`. Перед использованием прочитайте его README, интерфейсы, зависимости и отчёты.
4. Работайте в отдельной ветке `component/<id>-<task>` либо `layout/<project>-<task>`; для параллельных агентов используйте отдельные checkout/worktree.

## Изменения компонентов

- Один пакет: модель в `model/`, читаемые исходники в `src/`, `manifest.json`, README, проверки в `tests/`.
- Не редактируйте один двоичный файл одновременно с коллегой. Назначьте ответственного в задаче; при наличии файла используйте `git lfs lock <path>` и снимайте блокировку после согласованной передачи.
- После изменения скрипта синхронизируйте его с встроенным скриптом модели, сохраните модель и заново откройте её для проверки. Текстовый файл сам по себе не обновляет компонент VC.
- Для зависимостей используйте точную версию; при несовместимом интерфейсе увеличивайте major-версию.
- Единицы указывайте явно: геометрия mm, время s, скорость mm/s; значения из ТЗ в m/s переводите явно.
- Не переносите API RPro в VC без проверки. Укажите точную версию/сборку VC и версию встроенного Python, реально использованные при проверке.
- Не загружайте всю стороннюю библиотеку или установочные файлы; проверяйте право на распространение конкретного компонента.

## Доказательства

- Запустите `python tools/validate_catalog.py`.
- Для функционального изменения выполните сценарий в VC и добавьте отчёт по `templates/run-report.md`: commit, версия VC, параметры, seed, время моделирования, ожидаемый и фактический результат.
- Проверяйте сохранение количества грузов, лимиты буферов, взаимное исключение ресурсов, отсутствие зависаний, корректность reset и повторного запуска.
- Отделяйте факты заказчика, допущения и измерения. Не заменяйте отсутствующие данные выдуманными значениями.
- `draft` означает незавершённую разработку, `experimental` — проверку структуры, `validated` — наличие воспроизводимой проверки в VC. CI не подтверждает динамику модели.
- Если VC недоступен, явно пишите «симуляция не выполнена». Не присваивайте `validated`.
- Нельзя заявлять точность 5% без сравнения с независимыми натурными измерениями.

## Передача результата

Откройте Pull Request: что изменено, зачем, какие проверки выполнены, известные ограничения. Не объединяйте собственный PR без ревью коллеги. Не удаляйте чужие компоненты, не выполняйте force push в main, не сохраняйте токены/пароли в репозитории. Эти правила организационные; наличие серверной защиты ветки проверяется отдельно.
