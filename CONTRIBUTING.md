# Совместная работа

## Новый компонент

1. Создайте GitHub Issue с назначением, входами/выходами и критериями приёмки. Назначьте одного ответственного за двоичную модель.
2. Обновите `main` и создайте ветку:

```bash
git switch main
git pull --ff-only
git switch -c component/stu-initial
```

3. Скопируйте `templates/component/` в `components/<id>/`. Переименуйте `manifest.example.json` в `manifest.json`, заполните его и README. Пока модели нет, оставьте `model: null`, статус `draft`.
4. Добавьте файл модели в `model/`, скрипты в `src/`, сценарий проверки в `tests/`. Пути манифеста задаются относительно папки компонента.
5. Для изменения существующей модели сначала согласуйте владение в Issue и выполните `git lfs lock components/<id>/model/<file>`.
6. Выполните локальную проверку каталога и проверку в VC. Запишите результат в `results/`.
7. Добавьте конкретные файлы, сделайте commit и push, откройте Pull Request через GitHub. Укажите связанный Issue.

```bash
python tools/validate_catalog.py
git add components/<id> results/<report>.md
git commit -m "Add component and verification evidence"
git push -u origin HEAD
```

В командах замените `<id>` и `<report>` своими значениями. После принятия PR снимите свою блокировку `git lfs unlock <path>`.

## Использование чужого компонента агентом

Обновите репозиторий, выполните `git lfs pull`, прочитайте манифест и README, убедитесь в совместимости VC. Откройте тестовую сцену и повторите smoke-проверку. Исправления вносите отдельным PR, описывая влияние на зависимые планировки. Не считайте `validated` универсальной гарантией для другой версии VC.

## Настройка участников

Владелец добавляет конкретные GitHub-аккаунты через Settings → Collaborators, выдавая Write разработчикам. Каждый коллега и агент используют доступ своего пользователя; общий токен не передаётся. Читать и клонировать публичный репозиторий может любой. Приглашение collaborator необходимо для прямой отправки изменений и привязано к конкретному GitHub-аккаунту.

Рекомендуемые правила main: Pull Request, один независимый review, успешный `catalog`, запрет force push. Это описание желаемых настроек, а не подтверждение их включения; доступность серверной защиты зависит от тарифного плана и владельца репозитория.

Права администратора, публикация библиотеки и изменение состава участников остаются у владельца. Для инженерных данных заказчика используйте закрытый доступ. Оригиналы в `sources/private/` исключены из Git; их обмен согласуется отдельно.
